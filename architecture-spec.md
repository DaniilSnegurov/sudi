# Спецификация внутреннего конвейера обработки судебных документов

Версия 1.0, 3 октября 2026 года. Проектирование без реализации.

## 1. Назначение и границы

Вход: судебные приказы и исполнительные листы в PDF, постановления ФССП в XML, при наличии — соответствующие PDF. Входные файлы могут поступать одним пакетом ZIP.

Выход: таблица судебных документов, таблица ФССП и отчёт о документах с проблемами. Заголовки и порядок столбцов соответствуют предоставленным шаблонам. Дополнительно сохраняется машиночитаемый результат с источниками значений.

Основная схема: извлечение текста / OCR → извлечение фактов LLM → проверки → один дополнительный проход VLM по проблемным местам → разрешение полей по правилам → экспорт кодом.

OCR распознаёт текст на изображении. LLM связывает прочитанные сведения с людьми, датами, суммами и полями. VLM читает изображения спорных фрагментов. Код управляет процессом, проверяет ответы и формирует таблицы.

LLM и VLM вызываются через адаптер моделей; текущий провайдер доступа — OpenRouter. Выбор конкретных открытых моделей и OCR проводится после измерения качества на примерах. Языковая модель и модель со зрением могут быть разными. Архитектура не зависит от оборудования, конкретного имени модели и способа её размещения.

Интерфейс пользователя, инфраструктура развёртывания, внешние государственные сервисы, проверка подлинности документов и юридические заключения в эту спецификацию не входят.

## 2. Согласованные решения

| Правило | Решение |
|---|---|
| Основной должник | Явно указанный должник конкретного документа. Если такой участник не выделен — первый должник по порядку страниц и текста |
| Несколько должников | Сохранять всех. В экспортном перечне по образцу включать основного; количество — общее число уникальных участников-должников/ответчиков рассматриваемого спора |
| Основной долг | Вся основная задолженность, включая отопление и горячую воду, без пеней и расходов |
| Эталон против документа | Следовать документу. Расхождения эталона учитывать отдельно при оценке |
| Расхождение OCR и VLM | Не выбирать автоматически; спорную ячейку оставить пустой, оба кандидата внести в отчёт |
| Повторное чтение | Один дополнительный проход VLM по всем обнаруженным проблемным местам; без циклического перечитывания |
| Отсутствие значения | Пустое поле, не ноль |
| Проблемный документ | Сохранять уверенно извлечённые поля и указывать документ, проблемные поля и причины в отчёте |
| Таблицы | Заполняет программный код из структурированного результата |

Если карта документа содержит несколько явно выделенных должников, правило «первый» применяется среди них. При противоречии, которое не позволяет установить состав участников, экспорт перечня и количества остаётся нерешённым.

## 3. Единица обработки

Один судебный PDF создаёт одну строку судебной таблицы. Один XML ФССП создаёт одну строку таблицы ФССП по верхнему уровню постановления. Парный PDF ФССП не создаёт вторую строку.

Вложенные производства XML сохраняются отдельно внутри результата. Их реквизиты не подменяют верхний уровень и не создают дополнительные строки первой версии.

Первая версия предполагает один самостоятельный документ в одном PDF. Если обнаружены несколько самостоятельных актов, система не смешивает их: статус «Требует проверки», причина `MULTIPLE_DOCUMENTS`. Автоматическое разделение такого PDF отложено.

Связь XML/PDF сначала определяется по одинаковому имени внутри одной папки пакета, затем проверяется по доступным реквизитам документа: идентификатор, тип, номер и дата. Несогласованные пары помечаются. Сходство ФИО или номера дела само по себе не создаёт связь.

Точные дубликаты файлов определяются по контрольной сумме. Один документ обрабатывается один раз, а остальные пути сохраняются как его копии в отчёте пакета. Разные исполнительные документы по одному делу не объединяются. Отсутствие парного PDF не препятствует обработке полноценного XML.

При чтении ZIP допустимы только пути внутри рабочего каталога пакета; выход через абсолютные пути или `..` запрещён. При чтении XML внешние сущности и загрузка внешних ресурсов отключены. Эти правила выполняются до передачи содержимого моделям.

PDF ФССП без XML первой версией регистрируется как неподдерживаемый маршрут; судебным приказом его считать нельзя. Его включение в самостоятельный маршрут потребует отдельного профиля полей.

## 4. Модули и их контракты

| Модуль | Получает | Возвращает |
|---|---|---|
| Регистрация | Файл / пакет | Документы, пары, контрольные суммы, ошибки чтения |
| Чтение PDF | PDF | Страницы, изображения и извлечённые текстовые блоки |
| OCR | Изображение страницы | Блоки текста с координатами и доступными оценками распознавания |
| Разбор XML | XML | Типизированные поля верхнего уровня, текстовые блоки, вложенные сущности |
| Извлечение LLM | Текстовые блоки и профиль полей | Участники, реквизиты, адреса, обязательства, кандидаты значений с доказательствами |
| Проверки | Факты и источники | Список проблем и задания повторного чтения |
| VLM | Изображения фрагментов и точные вопросы | Прочитанные значения, подтверждающий текст либо «неразборчиво» |
| Разрешение полей | Кандидаты, правила, результаты VLM | Выбранные значения, состояния полей, нерешённые конфликты |
| Экспорт | Разрешённые поля | Две таблицы и отчёт о проблемах |

Каждый этап сохраняет входную версию, результат и причину завершения. Сбой одного файла не останавливает пакет. Повтор технически неудачного запроса не считается дополнительным смысловым проходом VLM: успешный ответ не запрашивается повторно для поиска более удобного значения.

## 5. Получение текста из PDF

### 5.1. Проверка страницы

Маршрут определяется отдельно для каждой страницы. Название файла, папки и наличие отдельных текстовых объектов не являются доказательством качественного текстового слоя.

Для страницы сохраняются исходные размеры, угол поворота, изображение и текстовые блоки. Текстовый слой проверяется на повреждённые символы, явно нарушенный порядок чтения и покрытие содержательных областей страницы. При сомнении запускается OCR всей страницы; текстовый слой остаётся дополнительным источником кандидатов.

Отсутствие текста не означает пустую страницу. В сканированных исполнительных листах нужные сведения находятся, в частности, на страницах 1, 3 и 5. Все страницы учитываются; автоматически исключается только уверенно пустая страница, что записывается в журнал покрытия. Служебные бланки могут не давать экспортных полей, но не должны исчезать из учёта.

### 5.2. Представление OCR

OCR должен возвращать блоки с текстом и координатами. Оценки уверенности слов/строк желательны, но их отсутствие не блокирует работу: остаются проверки формата, покрытия и противоречий.

Для блока сохраняются: `block_id`, номер страницы, исходный текст, координаты в системе исходной страницы, порядок чтения, способ получения, версия OCR и доступные оценки. Поворот и выравнивание скана должны иметь обратное преобразование координат.

Начальная настройка растеризации — 300 dpi, с ограничением размеров изображения по возможностям движка. Увеличение разрешения исходного низкокачественного скана не восстанавливает утраченные символы. Подготовленные изображения сохраняются отдельно от оригинала.

Слово или номер не исправляется молча. Очищенная версия текста хранится рядом с исходной; замены, влияющие на цифры или идентификаторы, требуют подтверждения источником.

### 5.3. Покрытие текста

Если на изображении обнаружен содержательный текстовый участок, которому не соответствует текстовый блок, возникает `TEXT_COVERAGE_GAP`. В VLM отправляется этот участок либо страница. Если область нельзя локализовать надёжно — страница целиком. Скрытый или ошибочный текстовый слой не получает безусловного приоритета перед видимым изображением.

## 6. Извлечение фактов моделью

Для обычного документа используется один основной смысловой вызов LLM с полным текстом всех страниц. Для набора это покрывает документы до восьми страниц без необходимости искусственно делить их по одной странице.

До запроса проверяются ограничения модели: вход вместе со схемой и резервом ответа должен помещаться в контекст. Если не помещается, документ получает `CONTEXT_LIMIT`; текст не обрезается. Автоматическое извлечение из произвольно длинных документов требует отдельного расширения с объединением фрагментов.

Модель получает стабильную схему, профиль типа документа и блоки, явно обозначенные как данные. Содержимое документов не меняет правила процесса и не запускает действия.

Модель возвращает факты, а не готовую строку таблицы:

- тип и форма документа;
- участников с ролями, порядком упоминания, вариантами ФИО и персональными реквизитами;
- отдельную ссылку на явно выделенного должника документа;
- судебное дело, судебный акт и исполнительный документ как разные наборы реквизитов;
- адреса с указанием владельца и назначения;
- обязательства: категория суммы, сумма, валюта, период, участники и вид ответственности;
- источники каждого факта и конфликты.

У каждой суммы хранится категория: основной долг, составляющая основного долга, пени, госпошлина, почтовые расходы, иные расходы, общая сумма взыскания или остаток. Дополнительно фиксируется, является ли сумма общей солидарной, индивидуальной либо указана «с каждого».

Повтор одной формулировки в нескольких разделах не создаёт новую сумму. Итог и его расшифровка не складываются. Сведения участников со сходными именами или одинаковыми синтетическими паспортами не объединяются только на этом основании.

Внутреннее представление поля:

```json
{
  "field": "principal_debt",
  "value": "121963.22",
  "state": "extracted",
  "derivation": "sum_of_components",
  "source_refs": ["p1_b18", "p1_b19"],
  "operands": ["37110.50", "84852.72"],
  "issue_ids": []
}
```

Деньги внутри структурированного результата представлены десятичной строкой; арифметика выполняется с десятичной точностью, не через двоичные числа с плавающей точкой. Это не определяет тип ячейки Excel: экспорт денег выполняется числом с двумя десятичными знаками.

## 7. Источники и нормализация

Для PDF источник содержит страницу, блок, цитату и при возможности диапазон символов внутри блока. Координаты берутся из чтения PDF/OCR, модель их не придумывает. Для VLM источник — предъявленный фрагмент изображения, его исходные координаты и ответ чтения.

Для XML источник содержит пространство имён и полный путь с индексами повторяющихся элементов, например `/f:OIp/f:IP[2]/f:IdDebtText`. Префикс `f` — обозначение известного URI, а не требование к префиксу во входном файле.

Код проверяет существование источника и присутствие цитаты в исходном тексте после ограниченной нормализации пробелов. Произвольное нечёткое сходство не считается доказательством. Производные значения, такие как сумма отопления и ГВС или ФИО в именительном падеже, отдельно отмечаются как нормализованные/вычисленные и сохраняют исходные формы.

Нормализация не восстанавливает утраченные цифры, не меняет содержательный адрес и не выводит отсутствующую дату из номера дела. Допустимы преобразование однозначной даты в ISO, пробелов в номере и десятичного разделителя в сумме.

Лица сопоставляются по явному повторению/связи в тексте, согласованным ФИО и дополнительным реквизитам. Явно указанные прежние фамилии сохраняются как варианты одного лица. Совпадение имени при конфликтующих существенных реквизитах требует проверки.

## 8. Правила выбора полей

### 8.1. Должник и персональные реквизиты

Сначала определяется явно выделенный должник документа, включая блок «Должником по исполнительному документу является» или верхнеуровневый `DbtrName` XML. Иначе выбирается первый из установленного списка должников.

Карточка выбранного должника имеет приоритет для его идентификаторов, даты рождения и адреса над цитатой судебного решения. Если карточка отсутствует, используется однозначно связанное упоминание этого человека. Выявленное противоречие сохраняется и делает документ требующим проверки, даже когда правило приоритета позволяет заполнить поле.

Если в равноприоритетных источниках разные значения — ячейка пустая. Расхождение OCR и VLM также всегда оставляет спорную ячейку пустой, независимо от приоритета раздела документа.

ФИО основного должника приводится к именительному падежу только при однозначности. Перечень соответчиков может сохранять падеж и варианты фамилий из документа, как допускает образец. Принадлежность каждой даты и каждого идентификатора устанавливается до выбора основного.

### 8.2. Суммы

Основной долг включает все явно присуждённые составляющие основной задолженности. Если дана общая сумма и её расшифровка, берётся общая, а расшифровка проверяется. Если даны только независимые составляющие одного обязательства — код складывает их и сохраняет операнды.

Солидарная сумма сохраняется полностью. Сумма «с каждого» сохраняется в размере для основного должника, не умножается на число людей. Индивидуальные суммы других участников не попадают в его поля.

Разные основания, периоды или группы ответственности сохраняются как отдельные обязательства. Их объединение допустимо только при полной, однозначной и непересекающейся структуре. Если один столбец не позволяет передать смысл без потерь, соответствующее поле остаётся пустым с `MULTIPLE_OBLIGATIONS`.

Госпошлина извлекается только при явном указании её назначения. «Судебные расходы» без расшифровки не записываются автоматически ни в госпошлину, ни в почтовые расходы. Расходы на отправку почтовой корреспонденции относятся к почтовым расходам, даже если сформулированы как судебные расходы.

Общая сумма взыскания и остаток задолженности не подменяют основной долг. Неизвестный основной долг не вычисляется вычитанием неподтверждённых составляющих из общего итога.

### 8.3. Периоды и даты

Период экспортируется для основного долга. Период пеней сохраняется отдельно внутри результата. Он не подменяет период основного долга.

Несколько несовместимых периодов, повреждённая дата или начало позже окончания создают проблему. Не выбирается первый период и не строится диапазон от минимальной до максимальной даты без доказательства непрерывного обязательства.

Дата судебного акта, выдачи исполнительного документа, вступления в силу и постановления ФССП различаются. При отсутствии нужной даты не используется ближайшая другая дата.

### 8.4. Адрес

Для XML `DbtrAdr` сохраняется точно по верхнему уровню. Его компоненты извлекаются из этого адреса. Тип улицы или помещения может уточняться другим согласованным упоминанием того же адреса, но другой адрес из судебного акта не подменяет текущий.

Для PDF приоритет имеет явно обозначенный адрес регистрации/основной адрес в карточке должника, затем адрес проживания, однозначно относящийся к нему. Несколько равноприоритетных адресов создают конфликт. Адрес взыскателя, суда или объекта потребления не становится адресом должника автоматически.

Корпус, строение, секция и комната сохраняются как самостоятельные компоненты внутри результата. При экспорте в ограниченные столбцы они передаются текстом: например, дом `20 корп. 1`, квартира/помещение `сек. 4, ком. 35`. Букву дома можно нормализовать по формату образца как `68/Б`; цифровой корпус нельзя превращать в квартиру или бесконтрольно заменять на дробь.

Почтовые и прочие расходы судебного PDF извлекаются во внутренний результат и участвуют в проверках. Новые столбцы в исходный шаблон не добавляются.

Парный PDF читается при конфликте или недостатке покрытия XML, а не автоматически на каждую строку. Если он повторяет дефект исходного текста, проблема остаётся. Прямые XML-поля продолжают сохранять исходные значения; несовпадение PDF создаёт предупреждение, а не молчаливую замену.

## 11. Проверки и задания VLM

Система не обещает обнаружить все ошибки OCR. Сигналы определяют подозрительные участки, а полнота обнаружения измеряется отдельно.

| Сигнал | Что проверяется | Действие |
|---|---|---|
| LOW_OCR_CONFIDENCE | Оценка OCR ниже порога профиля движка | Перечитать соответствующий фрагмент |
| INVALID_VALUE_FORMAT | Буква внутри суммы/идентификатора, невозможная дата, повреждённая структура | Перечитать источник |
| SOURCE_CONFLICT | Разные кандидаты одного поля | Перечитать оба фрагмента; затем применить правила приоритета |
| TEXT_COVERAGE_GAP | Содержательный участок изображения не представлен текстом | Перечитать участок или страницу |
| MISSING_ANCHORED_VALUE | Есть подпись вроде «ИНН», но значение не прочитано | Перечитать подпись с соседним текстом |
| UNCLEAR_OWNER | Неясно, к кому относится реквизит или сумма | Передать более широкий фрагмент с контекстом |
| INVALID_PERIOD | Начало позже конца / повреждённая дата | Проверить исходник; не восстанавливать по догадке |
| AMOUNT_RECONCILIATION | Полная явная расшифровка не совпадает с сопоставимым итогом | Проверить составляющие; не исправлять итог для сходимости |

Порог OCR задаётся отдельно для выбранного движка и калибруется на размеченных фрагментах. Сырые оценки разных движков не сравниваются как вероятности. Если оценок нет, состояние `confidence_unavailable` фиксируется, а остальные проверки продолжаются.

Проверки длины ИНН/СНИЛС/паспорта — сигналы возможной ошибки, а не повод дописать цифры. Проверка контрольных разрядов синтетических реквизитов учебного набора отключена. Будущие дополнительные проверки реальных данных также не имеют права изменять источник.

Отсутствие необязательного идентификатора без подписи/намёка не создаёт задания VLM. Если после дополнительного прохода не установлен основной должник, номер дела или дата акта, документ требует проверки. Отсутствие суммы в кратком тексте XML допустимо и не означает ошибку обработки, если источник её не содержит.

Для судебного профиля критичны тип документа, основной должник, номер дела и дата судебного акта. Для XML-профиля — тип и дата постановления, должник, номер исполнительного документа и его сумма. Отсутствие любого критичного поля создаёт `MISSING_CORE_FIELD`. Остальные поля могут отсутствовать без ошибки, если в источнике нет соответствующих сведений.

Оценки OCR сохраняются для всех блоков, но повторное чтение и пользовательская проблема создаются для участков, влияющих на извлекаемые сведения или их принадлежность. Плохо распознанная служебная строка сама по себе не делает все поля документа спорными.

Проверка арифметики выполняется только для явно сопоставимых величин. Исходная сумма, остаток, исполнительский сбор и иные суммы не считаются автоматически одной формулой. Денежные равенства проверяются в копейках; разницу 0,96 руб. нельзя скрывать допуском округления.

## 12. Дополнительное чтение VLM

Задания формируются одновременно после основных проверок. Один проход может включать несколько независимых запросов по разным фрагментам. Каждый проблемный фрагмент получает одну успешную попытку чтения; результат не запускает новый смысловой цикл.

Фрагмент включает окружающий текст, позволяющий определить владельца и назначение значения. При неизвестном расположении или зависимости от структуры используется полная страница. Первоначальный кандидат OCR/VLM не передаётся модели как подсказка ответа.

Ответ VLM: прочитанное исходное значение, цитата, указание связи с нужным полем либо `unreadable`/`ambiguous`. Формат проверяется кодом. Появление правдоподобного числа без подтверждения назначения не заполняет поле.

| Результат | Разрешение |
|---|---|
| Значения совпали после допустимой нормализации | Поле остаётся извлечённым, добавляется подтверждение VLM |
| Исходного кандидата не было, VLM прочитала однозначно | Кандидат может быть принят после проверки формата и принадлежности, источник — изображение |
| OCR/текстовый слой и VLM дали разные значения | Пустая экспортная ячейка, `READING_DISAGREEMENT`, оба кандидата в отчёте |
| Изображение подтвердило два разных значения в документе | `SOURCE_CONFLICT`; применяется только явно заданный приоритет источников, иначе пусто |
| VLM не прочитала | Поле остаётся нерешённым, `UNREADABLE` |
| Вызов не завершился технически | Поле остаётся нерешённым, `VLM_STAGE_FAILED` |

Совпадение OCR и VLM не является человеческой проверкой и не доказывает правильность. В XML смысловая ошибка или дефект исходника не лечатся OCR; VLM нужна только для чтения парного изображения, когда оно способно дать дополнительную информацию.

## 13. Состояния и экспорт

Состояния поля: `extracted` — выбранное значение, `not_found` — источник его не содержит, `needs_review` — не удалось выбрать надёжно, `confirmed` — подтверждено человеком в будущем процессе проверки. Отдельно хранится способ получения и список проблем. Выбранное по приоритету поле может иметь значение и предупреждение о противоречии.

Состояния документа:

- `processed`: обработка завершена без выявленных проблем;
- `needs_review`: есть неразборчивые значения, конфликты, неполнота обязательных сведений или неудачный дополнительный этап; надёжные поля сохраняются;
- `failed`: основной маршрут не дал пригодного результата из-за технической ошибки или неподдерживаемого формата.

На каждый зарегистрированный документ сохраняется запись результата. При `failed`, если профиль таблицы установлен, в соответствующей таблице есть строка с путём файла и доступными сведениями, а причина — в отчёте. Если профиль определить невозможно, файл учитывается только в общем отчёте, без произвольного выбора таблицы. Парные PDF и точные дубликаты не создают отдельные основные строки, но учитываются в отчёте пакета.

Основные результаты: `judicial.xlsx`, `fssp.xlsx`, `issues.xlsx`. CSV-экспорт тех же таблиц допустим как альтернативный формат: UTF-8 с BOM, разделитель запятая и корректное экранирование. XLSX содержит деньги как числа, даты как даты с отображением `yyyy-mm-dd`, идентификаторы и адресные номера как текст. CSV содержит даты ISO, деньги с точкой и двумя знаками после неё.

Отчёт проблем содержит: идентификатор документа, путь файла, статус, этап, поле, код и понятную причину, страницы/пути XML, кандидаты с источниками, влияние на экспорт и рекомендуемое действие сотрудника. Необработанные файлы включаются обязательно.

Результат без выявленных проблем называется именно так; название «без ошибок» не используется как гарантия. Отдельная сводка пакета показывает число успешных, требующих проверки, технически неудачных, парных и повторных файлов.

## 14. Контроль запросов и воспроизводимость

Вызов модели ограничен конкретной задачей и схемой ответа. У модели нет инструментов для изменения файлов или выполнения инструкций из документа. Именованные поля проверяются локально независимо от поддержки структурированного ответа провайдером.

Сохраняются идентификатор и доступная версия модели, провайдер, версии OCR, профиля полей и инструкций, параметры, ответы, время и стоимость. Автоматическая незаметная замена модели недопустима: при замене создаётся новая версия обработки.

Технические повторные попытки ограничены: максимум два повтора после исходного запроса при временной сетевой ошибке/ограничении частоты. Невалидный структурированный ответ допускает один запрос исправления формата без добавления новых фактов. Повторная ошибка фиксируется, бесконечного цикла нет.

Ручные исправления в будущем не должны затираться повторной обработкой. Новый запуск создаёт новую версию автоматического результата. Текущая спецификация описывает экспорт и доказательства для проверки; полноценный редактор не требуется для первой проверки конвейера.

## 15. Проверка качества и приёмка

Предоставленные эталоны — средство оценки, а не вход модели. Исходные таблицы не изменяются. Для выявленных расхождений создаётся отдельный реестр ожидаемых исправлений с источниками и применёнными решениями пользователя.

Оценка выдаёт два сравнения: с исходным эталоном и с исправленной по документам разметкой. Ошибка эталона, допустимая нормализация, неопределённость источника и ошибка извлечения учитываются отдельно.

Повторяющиеся дела/участники и парные документы находятся в одной группе при разделении набора для настройки и проверки. Нельзя настраивать модель на одном документе и считать почти одинаковый парный документ независимой проверкой.

Метрики: точность каждого поля, доля заполнения, доля правильных непустых ячеек, доля незамеченных ошибок среди непомеченных полей, доля документов на ручную проверку, покрытие источниками, время и стоимость. Результаты разделяются по сканам, текстовым PDF и XML.

Сравнение строковых идентификаторов строгое после удаления допустимых разделителей. Для участников сравнивается состав с учётом подтверждённых вариантов ФИО, а не только буквальное совпадение падежей. Деньги сравниваются точно до копейки. Пустота не считается равной нулю.

Числовые целевые показатели точности не заявлены без измерений. Качество выбранных моделей, калибровка OCR и доля пропущенных проблем — экспериментальная часть следующего этапа. Архитектура определяет поведение при любом результате этих измерений.

### Приёмочные сценарии

| Требование | Дано / когда / тогда |
|---|---|
| REQ-001: покрытие PDF | Дан восьмистраничный скан; при чтении учитываются все страницы, а реквизиты с 1, 3 и 5 связаны в одном документе |
| REQ-002: маршрутизация | Дан PDF из папки «электронные» без текста; при анализе страницы выбирается OCR |
| REQ-003: основной должник | В описании дела первым назван один человек, но карточка выделяет другого; при экспорте выбирается должник карточки |
| REQ-004: принадлежность | В документе есть ИНН взыскателя, но нет ИНН должника; ячейка ИНН должника остаётся пустой |
| REQ-005: повторы | Четыре человека перечислены в двух разделах; количество равно 4, а не 8 |
| REQ-006: состав долга | Даны отопление 37 110,50 и ГВС 84 852,72 без общего основного итога; основной долг равен 121 963,22 с двумя источниками |
| REQ-007: виды сумм | Есть итог и его детализация; итог не складывается с составляющими и не попадает в поле основного долга |
| REQ-008: госпошлина | Указано «по 266,66 с каждого»; поле содержит 266,66 для основного участника, без умножения |
| REQ-009: разногласие чтения | OCR и VLM возвращают разные суммы; ячейка пустая, документ и оба кандидата есть в отчёте |
| REQ-010: дефект источника | XML содержит повреждённую дату и несколько обязательств; система не придумывает период и помечает затронутые поля |
| REQ-011: XML-пути | XML содержит другие `DbtrName` и `IPNo` во вложенных `IP`; экспорт использует верхний уровень |
| REQ-012: отсутствие и ноль | Явная госпошлина 0 сохраняется числом 0; отсутствующая сумма остаётся пустой |
| REQ-013: почтовые расходы | Текст указывает расходы на отправку корреспонденции 182,40; `rub_post` содержит 182,40 |
| REQ-014: эталон | Эталон пустой, но СНИЛС читается и связан с должником; система извлекает его, оценка фиксирует расхождение разметки |
| REQ-015: частичный сбой | Один файл не читается; остальные обрабатываются, неудачный файл присутствует в отчёте |
| REQ-016: ограничение контекста | Документ не помещается в модель; текст не обрезается, причина явно записывается |
| REQ-017: экспорт | Строка с идентификатором с ведущим нулём проходит сохранение и повторное открытие без потери нуля |
| REQ-018: доказательства | Модель ссылается на несуществующий блок/цитату; значение не экспортируется автоматически |

## 16. Что готово и что проверяется следующим этапом

Согласованы архитектура, правила всех экспортных полей, маршруты источников, поведение при конфликтах и формат отчёта. Неопределённые значения конкретных документов не требуют новых бизнес-правил: они проходят в ручную проверку.

Перед реализацией модельного конвейера требуется обзор этой спецификации. Затем отдельно подготавливается план реализации. До нового запроса пользователя не запускаются OCR/VLM-запросы по набору, не заполняются итоговые таблицы и не создаётся продуктовый код.

Выбор конкретных движков и моделей должен опираться на будущий сравнительный прогон; он не меняет описанные контракты. Порог уверенности и целевые метрики утверждаются по результатам измерений, а не выбираются как обещание качества заранее.
